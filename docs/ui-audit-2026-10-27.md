# Sleep Puzzle — technical page audit

Date: 27 October 2026. Method: Impeccable audit, local browser inspection, source review, and the bundled detector. No application code was changed.

## Implementation integrity verdict

**Pass, with accessibility gaps concentrated in forms and the admin shell.** The public implementation expresses the documented Sleep Puzzle system: warm dark surfaces, self-hosted type, amber actions, responsive offer pieces, explicit unavailable states, and owner-managed copy. It does not need a visual replacement.

The detector returned **0 primary findings and 10 advisories** across `app`. This is not an accessibility certification: ERB template extensions are not configured in `.impeccable/config.json`, so templates were reviewed manually. The context launcher initially failed because its engine cache was unavailable; PRODUCT.md and DESIGN.md were read directly. The official engine was subsequently installed and used for the detector scan.

## P1 findings

### 1. Required password guidance is too faint

- **Category:** Accessibility / Theming.
- **Evidence:** `app/views/devise/shared/_field.html.erb:13` renders hints with `text-taupe-dark`. On mobile registration, computed text was `#57504a` on card surface `#2b2724`: **1.87:1**, below the normal-text AA threshold of 4.5:1. This includes “Minimum 6 znaków.” The same partial carries password reset and account-edit guidance.
- **Other affected locations:** `app/views/admin/shared/_translated_input.html.erb:17`, `app/views/admin/shared/_price_field.html.erb:23`, and `app/views/admin/articles/_form.html.erb:54` use the same token for meaningful instructions. These occurrences are source-confirmed, not separately rendered.
- **Impact:** Users can miss password requirements and editing instructions, especially in the product's intended tired-parent/nighttime usage scene.
- **Standard:** WCAG 1.4.3 Contrast (Minimum).
- **Recommendation:** Use a readable supporting-text token such as Taupe for enabled instructional copy; keep the faint token restricted to genuinely inactive UI. Check all enabled `text-taupe-dark` occurrences, and connect password hints using `aria-describedby`.
- **Suggested command:** `$impeccable harden`.

### 2. Admin editing fields have visible captions but no accessible names

- **Category:** Accessibility.
- **Evidence:** `app/views/admin/shared/_translated_input.html.erb:15` and `:31` use spans for field and language names; inputs at `:35`, `:39`, and `:44` have IDs but no associated labels or ARIA names. This partial is shared by product/package editing. Product kind, icon, and duration repeat the pattern in `app/views/admin/products/_form.html.erb:41`. Article title, excerpt, body, and other fields repeat it in `app/views/admin/articles/_form.html.erb:37` onward. `app/views/admin/shared/_price_field.html.erb:22` also leaves its select/text field unlabelled.
- **Impact:** Screen-reader users cannot reliably distinguish the purpose or language of the editing fields. Clicking the visible caption does not focus its input either.
- **Standard:** WCAG 1.3.1 Info and Relationships; 4.1.2 Name, Role, Value.
- **Recommendation:** Give every control an associated label, including both field purpose and language (for example “Opis — Polski”). Label the Trix editor appropriately and associate hints separately. Preserve the working CMS field-label pattern in `admin/content_blocks/_field_input.html.erb`.
- **Suggested command:** `$impeccable harden`.

### 3. The admin document does not declare its language

- **Category:** Accessibility.
- **Evidence:** `app/views/layouts/admin.html.erb:2` emits plain `<html>`. The panel is intentionally Polish-only; unlike the public layout it has no locale controller to set document language.
- **Impact:** Assistive technology may pronounce the entire Polish panel using the browser/default document language.
- **Standard:** WCAG 3.1.1 Language of Page.
- **Recommendation:** Emit `lang="pl"` on the admin document and verify that public-to-admin Turbo navigation updates the root language as well as direct page loads. Preserve Polish-only administration.
- **Suggested command:** `$impeccable harden`.

## P2 findings

### 4. The mobile admin sidebar lacks focus and motion handling

- **Category:** Accessibility / Responsive.
- **Evidence:** `app/frontend/controllers/sidebar_controller.js:111` opens an overlay by removing `hidden` and translating the panel. It does not move focus into it, isolate the covered content, handle Escape, or restore focus after close. The overlay markup in `app/components/sidebar/component.html.erb:3` has no dialog semantics. Closing at controller line `:136` waits 300ms; neither this controller nor the sidebar CSS has a reduced-motion alternative.
- **Impact:** Keyboard focus can remain behind the overlay, and a keyboard/screen-reader user can traverse covered content rather than the opened navigation. Motion preference is ignored for this sliding panel. Source-confirmed; authenticated runtime behavior remains to be exercised.
- **Standard:** Review against WCAG 2.4.3 Focus Order. Reduced-motion accommodation is also a product quality requirement; this alone is not claimed as an AA failure.
- **Recommendation:** Treat the overlay as a labelled modal navigation surface, with initial focus, background isolation, Escape, and focus restoration. A native dialog is an option. Make open/close immediate when reduced motion is requested.
- **Suggested command:** `$impeccable harden`.

### 5. Admin touch targets fall below the project's mobile minimum

- **Category:** Responsive.
- **Evidence:** The mobile sidebar opener is `size-9` (36px) at `app/components/sidebar/component.html.erb:133`; its close button is `size-10` (40px) at `:61`. CMS locale tabs use 14px text with 6px vertical padding at `app/views/admin/content_blocks/_section_form.html.erb:15`, without a 44px minimum. Article language tabs use the same pattern.
- **Impact:** Frequent actions are harder to hit reliably on a phone and differ from the public navigation's 44px minimum.
- **Standard:** PRODUCT.md / DESIGN.md 44px target commitment. Do not equate this with a WCAG 2.1 AA target-size requirement: the 44px WCAG 2.1 target criterion is AAA.
- **Recommendation:** Apply 44px minimum hit areas to these controls, preserving compact icon artwork inside the larger area; verify spacing and mobile header clearance together.
- **Suggested command:** `$impeccable adapt`.

### 6. Unrelated frontend controllers load on every public page

- **Category:** Performance.
- **Evidence:** `app/frontend/controllers/index.js:6` eagerly imports every controller except Cally. Consequently public reading pages include admin editor/upload/sidebar logic and carousel/tooltip dependencies. For example, `carousel_controller.js:2` imports Embla and wheel gestures, and `tooltip_controller.js:2` imports Floating UI. The existing generated `public/vite-dev/assets/application-BTiA-4vW.js` is approximately 301KB uncompressed; this is an existing artifact size, not a fresh production build or a network timing measurement.
- **Impact:** Visitors download and parse code unrelated to their current task; the cost is shared across entry pages, including the mobile first visit.
- **Recommendation:** Extend the existing feature-loading approach in `app/frontend/lib/page_features.js` to admin-only controllers and optional carousel/tooltip features. Keep shared navigation/form controllers immediately available. Compare a fresh production build and cold-load mobile timings before/after, and verify first interaction on Turbo visits.
- **Suggested command:** `$impeccable optimize`.

### 7. Form instructions and errors are not consistently connected to controls

- **Category:** Accessibility.
- **Evidence:** `app/views/bookings/_form.html.erb:10` passes error and required metadata into the wrapper, but the input at `:12` and select at `:29` do not receive `aria-invalid`/`aria-describedby`, and the required flag is not passed to those editable native controls. The booking frame has no live error announcement or explicit focus recovery. `app/views/devise/shared/_field.html.erb:13` emits hints without IDs or input association (confirmed in registration DOM). `app/views/testimonial_invitations/show.html.erb:15` sets invalid state but leaves the adjacent error unassociated.
- **Impact:** A user revisiting a failed field may hear its name and value without the reason it failed or the relevant instruction. Booking frame replacement can also remove the focused submit control without directing attention to the error.
- **Standard:** Programmatic relationships should be checked against WCAG 1.3.1; validation recovery against 3.3.1. This is a verified implementation gap, not a claim that every current error state is unusable.
- **Recommendation:** Follow the contact form's existing pattern: stable error IDs, `aria-describedby`, `aria-invalid`, and required state on the input itself. Give the booking response a concise live summary or focused error summary. Associate normal hints too. Test server validation, a stale slot, and unavailable package pricing.
- **Suggested command:** `$impeccable harden`.

## Detector interpretation and exclusions

The 10 advisories concerned CMS preview highlight color/radius (2), a 10px tooltip size (1), and white/translucent black literals in CSS/viewer code (7). These are advisory evidence, not 10 additional user-facing defects. Viewer backdrops are intentional; local CMS highlighting is internal tooling. The old white `div.form-control` rule has no demonstrated active use. Tooltip sizes need usage-specific inspection before being treated as a finding.

The apparent light select defaults are overridden by `select.form-control:not([multiple])` at `app/frontend/entrypoints/application.css:458`; they are **not** reported as a broken dark-select bug. Missing image width/height attributes were not automatically counted as layout shift where wrappers already reserve geometry. Empty decorative alt text, native disclosures, deliberate Polish fallback, and the calendar's service-unavailable state were not treated as defects.

## Patterns and positive findings

The recurring gap is shared accessibility contracts: field captions do not always become labels, wrapper metadata does not automatically reach inputs, and the public navigation's focus/target standards do not extend to the admin shell. Fix shared partials before adjusting individual pages.

Preserve these strengths:

- Public skip link and focusable main landmark; visible amber focus on principal navigation and actions.
- Readable primary/secondary text, fluid gutters, wrapping headings, and successful sampled mobile reflow.
- Native reading disclosures and native package/calendar dialogs, with explicit state in the related controllers.
- Contact form labels, associated errors, live frame, autocomplete, and submitting feedback.
- Separate unavailable versus genuinely empty calendar states, including retry and direct contact recovery.
- Self-hosted variable fonts; integration loading deferred until interaction; lazy calendar/editor/viewer boundaries.
- Purchase safeguards and retained pending/unavailable states instead of fabricated prices or success claims.

## Recommended action order

1. **P1 — `$impeccable harden`:** Correct hint contrast, admin labels, and document language; then complete form error relationships and sidebar focus behavior.
2. **P2 — `$impeccable adapt`:** Bring admin navigation and language tabs to 44px targets and check mobile header clearance.
3. **P2 — `$impeccable optimize`:** Split optional/admin controllers from the public entry bundle and measure the resulting production load.
4. **Verification — `$impeccable audit`:** Recheck populated commerce states, authenticated screens, keyboard flow, enlarged text, and screen-reader announcements after fixes.
5. **Finish — `$impeccable polish`:** A bounded visual consistency pass after functional and accessibility corrections.

These commands can be run individually, together, or in a chosen order. Re-run `$impeccable audit` after fixes to update the provisional score.
