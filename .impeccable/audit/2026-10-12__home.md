# Front-page technical audit

Date: 2026-10-12 (Europe/Warsaw)

Target: `http://localhost:3000/`, current local Rails application, signed-out Polish visitor.
Primary source: `app/views/home/index.html.erb`, including the shared navigation,
footer, styles, and JavaScript entrypoint. Product and design context: `PRODUCT.md`
and `DESIGN.md`.

## Implementation integrity verdict

**Pass for product-specific coherence, with issues to resolve.** The rendered page
uses the established warm dark surfaces, amber actions, Baloo 2/Quicksand pairing,
and a literal puzzle joint between the two offer links. Content remains editable
through the CMS. Native links and buttons preserve the core actions. This is a
coherent Sleep Puzzle interface, rather than an unrelated template.

The runtime product description conflicts with the implemented audio delivery,
and the local hero portrait fails to load. The bundled detector found **0 primary
anti-patterns and 7 advisories** in the requested home-template/CSS scan. Those
results do not supersede browser evidence or establish accessibility conformance.

## Detailed findings

### [P1] Tab skips the remaining mobile navigation links

- **Location:** `app/frontend/controllers/navbar_controller.js:883`, also selectors
  at lines 892, 919, 939, 965 and 987.
- **Category:** Accessibility.
- **Verified reproduction:** At 390px, focus Menu and press Enter. Focus moves to
  the menu's Audioproces link. Press Tab: the menu closes and focus jumps to the
  main-page Audioproces offer card, skipping Współpraca 1:1, English, and Zaloguj się.
- **Cause:** Every forward Tab while the menu is open is prevented and redirected
  outside the dropdown. Several focusable-element selectors also use the
  nonexistent `buttons` tag instead of `button`.
- **Impact:** People following normal sequential keyboard navigation cannot reach
  all expanded links. ArrowDown works as a workaround, but users must discover it;
  arrow support does not replace Tab for a disclosure navigation pattern.
- **Standard:** WCAG 2.4.3 Focus Order concern. The
  [W3C disclosure navigation guidance](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)
  explicitly retains Tab/Shift+Tab through expanded links alongside optional arrows.
  Full assistive-technology conformance testing remains outstanding.
- **Recommendation:** Let native Tab advance through visible menu links. Close on
  Escape or when focus actually leaves navigation, preserve Escape focus return,
  and correct the selectors. Verify forward and reverse traversal for mobile,
  language, and signed-in profile panels.
- **Suggested command:** `$impeccable harden front page`.

### [P1] Hero portrait fails in the audited local environment

- **Location:** `app/views/home/index.html.erb:13`; image generation in
  `app/helpers/application_helper.rb:78`.
- **Category:** Implementation integrity / asset resilience.
- **Evidence:** The Karola image is visibly broken on desktop. After loading has
  finished, `complete` is true and `naturalWidth` is 0. It reserves roughly a
  417px square on desktop and leaves an empty portrait region on mobile.
- **Impact:** The first screen loses the owner image that supports trust and
  allocates a large area to a failed asset. Visual approval from this local page
  would be misleading. This is not evidence that production has the same fault.
- **Cause boundary:** The template fallback handles a missing attachment record,
  but a present record whose variant cannot be fetched still produces an image
  tag and bypasses that fallback. The storage/variant failure cause was not traced.
- **Standard:** Asset reliability; no independent alt-text violation asserted,
  because the image has the name Karola.
- **Recommendation:** Verify that local attachment bytes and variant processing
  are available. Add a meaningful load-error fallback if attachment failures must
  be tolerated; retain the existing mascot fallback for absent content.
- **Suggested command:** `$impeccable harden front page`.

### [P2] Header and footer controls miss the 44px touch-target goal

- **Location:** `app/components/navbar/component.rb:83`,
  `app/views/shared/_cart_badge.html.erb:4`,
  `app/views/shared/_footer.html.erb:25`; desktop utility controls in
  `app/views/shared/_navbar.html.erb:76`.
- **Category:** Responsive design / accessibility.
- **Measured sizes:** Mobile Menu is 34×34px; cart is 36×36px. Footer links are
  about 17.5px high. Desktop navigation links are about 41.6px high, the language
  trigger 35.6px, and sign-in 38px.
- **Impact:** Small hit areas make one-handed use less forgiving for the tired
  parent identified in PRODUCT.md. Larger offer cards and the 54px closing CTA
  already show that comfortable targets fit this interface.
- **Standard:** The project audit goal is 44×44px. That corresponds to
  [WCAG 2.1 SC 2.5.5, Level AAA](https://www.w3.org/WAI/WCAG21/Understanding/target-size);
  these measurements alone do not establish a WCAG 2.1 AA failure.
- **Recommendation:** Give header controls minimum 44px dimensions and make
  standalone footer links block targets with suitable vertical padding. Preserve
  reading size and section spacing; enlarge the hit area rather than just the icon.
- **Suggested command:** `$impeccable adapt front page`.

### [P2] The public page eagerly loads editing and unrelated feature code

- **Location:** `app/frontend/entrypoints/application.js:8`, lines 11 and 17–19;
  `app/frontend/controllers/index.js:4`.
- **Category:** Performance.
- **Evidence:** The shared entrypoint statically imports Active Storage, Cally,
  Trix, Trix CSS and Action Text. The eager controller glob imports every
  controller, including admin upload/CMS code, PhotoSwipe, calendar code and its
  dayjs locales, and carousel dependencies. The signed-out front page has no
  editor, calendar, upload control or lightbox.
- **Impact:** Visitors incur avoidable JavaScript download and parse work before
  needing those features. No measured production byte saving or frame-rate claim
  is made here. A carousel dependency may be needed when real testimonials exist.
- **Standard:** Performance efficiency; no WCAG violation asserted.
- **Recommendation:** Separate editor/upload dependencies into the admin bundle,
  and load feature controllers/dependencies when their elements appear. Preserve
  Action Text display styling on public rich content and Turbo navigation behavior.
- **Suggested command:** `$impeccable optimize front page`.

### [P2] The audio offer describes video delivery

- **Location:** `app/views/home/index.html.erb:34`, CMS field `home.choices.audio`.
  Delivery implementation: `app/models/product.rb:155` and
  `app/controllers/products_controller.rb`.
- **Category:** Implementation integrity / content accuracy.
- **Evidence:** The currently rendered Polish description says “24 krótkie nagrania
  wideo”, under Audioproces, then says they can be listened to during settling.
  The confirmed product record and repository implement audio chapters, audio
  streaming and an audio trailer. The repository does not establish video delivery
  or verify the stated count of 24. The YAML fallback is a different, generic
  listening description; this mismatch is in current CMS content.
- **Impact:** A visitor may expect a video course when evaluating an audio offer.
- **Standard:** Product truth; no WCAG violation asserted.
- **Recommendation:** Confirm the actual medium and chapter count with the owner,
  then correct the CMS description to the confirmed offer. Do not hardcode a
  substitute or silently invent a count.
- **Suggested command:** `$impeccable clarify front page`.

### [P2] Navigation animation has no reduced-motion alternative

- **Location:** `app/components/navbar/component.rb:67`;
  `app/frontend/controllers/navbar_controller.js:632` and lines 688–695.
- **Category:** Accessibility / motion.
- **Evidence:** Navigation uses scale transitions, animated left/width/height,
  and blur/fade when panels switch. Neither the navbar component nor its
  controller checks reduced motion. The stylesheet's reduced-motion-aware
  library-row treatment does not cover navigation.
- **Impact:** Visitors requesting less motion still receive nonessential menu
  movement. Layout-property animation also merits simplification, though frame
  drops were not measured and are not asserted.
- **Standard:**
  [WCAG 2.1 SC 2.3.3, Level AAA](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions.html),
  plus the Impeccable motion floor; not an asserted AA failure.
- **Recommendation:** Provide an instant state change or restrained opacity
  alternative for reduced motion, preserving focus, expanded state and hierarchy.
  Avoid a global near-zero-duration override that breaks state timing.
- **Suggested command:** `$impeccable animate front page`.

### [P3] The offer's corner scale differs from its documented authority

- **Location:** `app/frontend/entrypoints/application.css:728`, lines 761, 793 and
  807; also the hero's `rounded-3xl` at `app/views/home/index.html.erb:13`.
- **Category:** Theming / design-system documentation.
- **Evidence:** The detector reports four instances of 1.5rem corner radii outside
  DESIGN.md's scale. The current paired offer and portrait use 24px corners while
  documented container corners are 16px.
- **Impact:** Future work has two conflicting radius references. This is an
  intentional-looking implementation difference, not a measured usability defect.
- **Standard:** Project design authority; no WCAG violation.
- **Recommendation:** At a requested documentation or refinement pass, decide
  whether 24px is an approved addition and record it, or align the implementation
  with the current scale. Do not flatten the puzzle joint merely to satisfy a scan.
- **Suggested command:** `$impeccable document`.

## Detector advisories reviewed in context

- Four radius advisories correspond to the documented-scale discrepancy above.
- `#fff` at CSS line 243 belongs to an unused scaffold form-control rule, not
  an element rendered on this front page. It is not a visible home-page violation.
- Two black-alpha advisories at CSS lines 832 and 858 belong to consultation
  modal treatments. They are outside this page's rendered scope and do not justify
  changing the home-page palette.
- No generic font substitution or light-mode toggle is recommended: the
  self-hosted rounded pairing and permanently dark theme are binding project choices.

## Patterns and systemic issues

Navigation mixes disclosure semantics with menu-style keyboard handling. Its
reusable controller makes the Tab defect relevant beyond the mobile home page.
Small utility targets recur in the shared chrome, and the public/admin shared
entrypoint repeats unnecessary imports across every public route. CMS copy and
design documentation can diverge from the implementation without producing a
primary detector finding.

## Positive findings

- No document overflow or out-of-viewport visible elements found at 320px; document
  scroll width also equals viewport width at 390, 768 and 1440px.
- Offer cards stack on mobile and form two equal columns at 768px. At that width,
  both cards measure approximately 364×329px.
- One page H1, section H2s, footer H3s, and navigation/main/footer landmarks are
  present in the rendered page. Decorative icons have accessible hiding and the
  cart/menu have names.
- Menu Enter opening, ArrowDown traversal, Escape closing and focus return work.
  Offer-card keyboard focus has a visible 2px amber outline. The cart retains a
  visible browser focus outline, though it differs from the documented amber style.
- Verified text-color pairs meet AA normal-text contrast: cream/ink 14.61:1,
  tan/ink 9.90:1, accent/surface 5.98:1, taupe/footer 5.89:1. The primary CTA's
  ink/amber pair measures 6.69:1.
- Variable WOFF2 fonts are self-hosted with Latin and extended-Latin subsets and
  `font-display: swap`. CMS portrait variants cap image dimensions; the hero
  reserves an aspect ratio rather than relying on late image dimensions.
- The initial signed-out document has no external script tag; fonts/assets are
  local, and Paddle loading is deferred by the checkout integration. This is not
  a full network/privacy certification.
- No console warnings or errors were returned by the browser log snapshot.

## Verification limits

Desktop full-page and mobile viewport captures were inspected, alongside DOM
geometry, computed colors, keyboard state, source code, and the bundled detector.
The browser's mobile screenshot preview scaled unexpectedly after a viewport
override, so mobile geometry conclusions rely on the measured CSS viewport and
DOM bounds. The desktop capture is the reliable visual reference for the image
failure. The default viewport was restored afterward.

Production, signed-in/profile states, actual screen-reader behavior, forced colors,
browser text-only zoom, and low-end-device timing were not tested. No production
Core Web Vitals or bundle-size numbers are claimed. FAQ and testimonial collections
are empty in the current local page; their source was inspected but populated
states were not created or browser-tested. The absent sections are intentional
empty-state behavior, not findings. The long reading section and lack of a hero
CTA are UX critique topics, not technical defects asserted in this audit.
